## 一、演进脉络

```text
Go GC 演进:
────────────────────────────────────────
Go 1.0 ~ 1.7:  串行标记-清除 (STW)
Go 1.8:        并发标记，但扫描阶段仍有停顿
Go 1.5:        三色并发标记 (tri-color)
Go 1.8+:       混合写屏障 (hybrid write barrier)
Go 1.25:       Green Tea GC 实验性引入
Go 1.26:       Green Tea GC 默认启用
```

## 二、Green Tea GC 核心设计

### 2.1 问题定义

传统 GC 在小对象扫描时存在**缓存局部性差**和**CPU 可扩展性不足**的问题：

```text
传统 GC 扫描模式:
────────────────────────────────────────
对象布局: [obj1][obj2][obj3]...[objN]（分散在堆中）
扫描行为: 随机访问 → cache miss → 串行处理

Green Tea GC 扫描模式:
────────────────────────────────────────
对象布局: 按 8KB span 分组
扫描行为: 批量顺序访问 → cache hit → 向量化处理
```

### 2.2 形式化模型

```text
Green Tea GC 标记阶段:
────────────────────────────────────────
输入: 根集合 R，堆 H（划分为 span 集合 S）
输出: 存活对象集合 L

对于每个 span s ∈ S:
    并行扫描 s 中的所有对象
    使用 SIMD 指令批量检查对象标记位
    如果对象存活，将其引用对象加入工作队列

优化点:
├─ 按 span 顺序扫描（空间局部性）
├─ 8KB span 大小与 CPU cache line 对齐
├─ 向量指令（AVX-512/AVX2）加速位图扫描
└─ 减少跨 NUMA 节点访问
```

## 三、性能数据

| 指标 | 传统 GC | Green Tea GC | 提升 |
| ------ | --------- | ------------- | ------ |
| GC overhead | 基准 | -10%~-40% | 显著 |
| 扫描吞吐量 | 基准 | +15%~+30% | 中等 |
| tail latency (P99) | 基准 | -20%~-35% | 显著 |
| CPU 利用率 | 单核瓶颈 | 多核扩展 | 结构性 |

**AMD64 向量优化**（Intel Ice Lake / AMD Zen 4+）：

- 额外约 10% GC overhead 降低

## 四、调优与监控

```go
// 禁用 Green Tea GC（Go 1.26 临时回退）
// go build -tags=nogreenteagc
// 或环境变量: GOEXPERIMENT=nogreenteagc

// 监控 GC 指标
import "runtime/metrics"

func printGCMetrics() {
    samples := []metrics.Sample{
        {Name: "/gc/cycles/automatic:gc-cycles"},
        {Name: "/gc/heap/allocs:bytes"},
        {Name: "/gc/heap/frees:bytes"},
    }
    metrics.Read(samples)
    for _, s := range samples {
        fmt.Printf("%s: %v\n", s.Name, s.Value)
    }
}
```

## 五、生产注意事项

1. **回退开关预测未成真（复盘）**：本文曾预测 Go 1.27 将移除 `GOEXPERIMENT=nogreenteagc` 回退开关。实际情况：截至 Go 1.27.1，Green Tea GC 仍为 `GOEXPERIMENT=greenteagc` 实验（未默认启用），`nogreenteagc` 开关仍存在
2. **bit-for-bit 输出可能变化**：`image/jpeg` 等包在 1.26 已重写
3. **内存布局变化**：64位堆基址随机化可能影响某些 CGO 场景
